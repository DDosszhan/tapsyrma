# Tapsyrma — архитектура на VPS

Статус: целевая схема, 12 октября 2026. Реализованный путь описан в README. Ниже остаются планы на ограничения частоты ввода кода, лимит времени сдачи, журнал изменений, экспорт, резервные копии и нагрузочное испытание; эти функции еще не готовы. Исходные условия: 9-й и 10-й классы, до 100 учеников одновременно; администратор создает экзамены, учитель выбирает ученика и экзамен, затем выдает персональный код на одну попытку; Tapsyrma сохраняет попытки и показывает баллы, а оценку в EduPage учитель меняет сам.

## Размещение

Один VPS со скриншота: 3 vCPU, 8 ГБ RAM, 100 ГБ NVMe, 13 250 ₸/мес. На нем размещаются фронт, один API-сервер и PostgreSQL. Supabase и Cloudflare Pages в основной схеме не используются.

```text
Браузер ученика/учителя
          │ HTTPS
          ▼
        Caddy ── статические файлы фронта
          │
          └────── Django/Gunicorn ── PostgreSQL (только внутренняя сеть)
                      │       └── приватные файлы силлабуса
                      └────────── OpenAI API (генерация и проверка открытых ответов)
```

Реализация: один проект, пять сервисов в Docker Compose (Caddy, Django/Gunicorn, generator, worker, PostgreSQL), постоянные тома для данных. Фронт — страницы Django и небольшой JavaScript для экзамена и автосохранения; отдельная SPA-сборка не требуется. Caddy отдает статические файлы и получает HTTPS-сертификат для домена. Браузер обращается только к Django; соединение с базой и ключ OpenAI в браузер не попадают.

Стек: Python, поддерживаемая ветка Django LTS, PostgreSQL, Gunicorn, Caddy, Docker Compose. Django предоставляет авторизацию, сессии, CSRF-защиту, миграции и административный интерфейс. Для OpenAI Responses API используется стандартная библиотека Python и Structured Outputs. Отдельные Redis, Celery, React и Next.js не нужны на первом этапе.

## Вход и права

Учителя и администраторы входят в стандартную админку Django. Только администратор создает и меняет экзамены; учитель выдает коды на утвержденные экзамены и видит результаты. Администратор создает ученику учетную запись с почтой или загружает список из Excel. Начальный пароль хранится в приватной конфигурации и обязательно меняется при первом входе. Ученик входит по почте и паролю, а персональный код дает доступ только к назначенному ему экзамену. Сдачи связаны с постоянной записью ученика, поэтому история доступна после следующего входа.

Класс хранится у ученика и проверяется при выдаче приглашения. Ученик видит только собственные сдачи и по коду получает доступ только к одной назначенной работе. Все видят список опубликованных экзаменов, но вопросы и ключи открываются только владельцу попытки в нужный момент.

## Персональный код на один экзамен

1. Учитель выбирает ученика и один утвержденный экзамен, задает время, до которого можно начать. Система создает отдельное приглашение со случайным кодом из 8 удобочитаемых символов. Код показывается учителю для личной выдачи ученику; в базе хранится HMAC кода с серверным секретом, а не сам код.
2. Ученик входит по почте и паролю, затем вводит код. Сервер сверяет владельца кода с вошедшим учеником. Он видит свое имя и название экзамена, затем подтверждает старт. Просмотр условий попытку не расходует.
3. После выдачи кода фоновый generator сохраняет отдельный вариант для приглашения. Старт доступен только при статусе «Готов». При старте сервер закрепляет одну попытку за кодом. Повторный ввод того же кода во время работы возвращает ту же попытку и сохраненные ответы, в том числе после обрыва связи; второй вариант не создается.
4. После сдачи код больше не открывает работу. Если нужна еще одна сдача, учитель явно выдает новое приглашение; первое и все его результаты остаются в истории. Потерянный код активной попытки можно перевыпустить без создания новой попытки.

После окончания времени входа новые старты запрещены, но уже начатую работу можно продолжить. Ограничение частоты неверных кодов остается задачей перед массовым запуском. Общий начальный пароль создает риск захвата учетной записи до первого входа ученика; при выдаче реальных аккаунтов лучше перейти на персональные временные пароли или подтверждение почты. Для суммативов учитель выдает код лично и сверяет ученика в классе.

## Подготовка экзамена и вариантов

1. Администратор создает экзамен для 9-го или 10-го класса, задает название, предмет, общее число вопросов и баллов. Он вставляет нужную часть силабуса текстом или загружает TXT, PDF либо DOCX. Храним оригинал приватно и извлеченный редактируемый текст; администратор проверяет его перед генерацией. Для PDF-скана без текстового слоя нужен OCR или ручная вставка текста.
2. Администратор добавляет нужные типы вопросов: сначала MCQ с одним правильным ответом и открытый ответ. Для каждого включенного типа указывает количество и баллы за вопрос; ненужный тип удаляет. Суммы по типам обязаны совпадать с общим числом вопросов и баллов. Для равной структуры вариантов далее задаются требования силабуса и сложность по каждой группе заданий.
3. После выдачи кода generator отправляет в OpenAI API текст силабуса и получает структурированный персональный вариант. При проверке открытого ответа туда же отправляются вопрос, рубрика, образец и текст ответа ученика без имени или ID. Учет токенов и расходов еще не реализован.
4. Администратор может проверить формулировку, фактологию и ключ каждого готового варианта до урока. Вопросы сохраняются вместе с критериями и объяснениями; они не меняются после сдачи.
5. При старте попытки сервер берет заранее сохраненные вопросы только этого приглашения. Другой ученик получает отдельные записи вопросов по той же структуре экзамена.

Равная структура вариантов не доказывает равную фактическую сложность. Перед важным экзаменом администратор проверяет готовые персональные варианты. ИИ оценивает открытые ответы по сохраненным критериям; итоговую оценку в EduPage решает учитель.

## Попытки и результаты

Основные данные: `students`, `exams`, `syllabus_sources`, `blueprints`, `question_versions`, `answer_keys`, `exam_invitations`, `attempts`, `attempt_questions`, `responses`, `results`, `audit_events`.

- `start_attempt` в одной транзакции проверяет приглашение, срок начала и статус кода; сохраняет вариант и версию ключей. Уникальное ограничение базы на `attempt.invitation_id` исключает вторую попытку даже при двух одновременных нажатиях. Повторный запрос возвращает существующую попытку.
- Ответы сохраняются автоматически примерно раз в 10–15 секунд и при переходе между вопросами. Интерфейс показывает статус сохранения; неподтвержденные ответы временно остаются в браузере при обрыве связи.
- `submit_attempt` выполняется одной транзакцией и идемпотентно: повторное нажатие возвращает тот же результат. Время берется с сервера. После отправки ответы не меняются; исправление балла записывается отдельным событием с автором и причиной.
- Попытки со статусами «в процессе», «ожидает проверки», «проверяется», «проверено» и «нужна ручная проверка» сохраняются вместе с ответами, вариантом и баллами. Учитель видит историю в админке. Перенос оценки в EduPage остается ручным.

## Надежность и эксплуатация

- При 100 учениках и сохранении каждые 15 секунд средняя нагрузка автосохранения составляет около 7 записей в секунду. Это умеренная нагрузка для данной конфигурации при коротких запросах и индексах. Пик одновременного входа и отправки проверяется отдельно; паспортные 3 vCPU/8 ГБ сами по себе не гарантируют результат.
- Ориентир по памяти: до 2 ГБ на PostgreSQL, до 2 ГБ на приложение с несколькими воркерами, остальное — ОС, файловый кэш и запас. Точные параметры задаются после измерения, а не по этой оценке.
- PostgreSQL не открывается в интернет; извне доступны только HTTPS и ограниченный SSH. Секреты хранятся вне репозитория. Обновления ОС и зависимостей выполняются регулярно.
- Ночью создается копия базы через `pg_dump` и копия приватных файлов. Они шифруются и отправляются **за пределы VPS**. После каждого сумматива делается дополнительная копия результатов. Раз в месяц выполняется пробное восстановление.
- Мониторинг проверяет доступность сайта и API, свободное место, память, работу базы и успешность последней резервной копии. До экзамена проводится тест ввода кодов и сохранения на 100 одновременных учеников из школьной сети.
- Один VPS остается единой точкой отказа. Внешняя копия позволяет восстановиться, но не обеспечивает мгновенное переключение при аварии; для важного сумматива нужен запасной порядок сдачи.
- Скриншот тарифа не подтверждает SLA, резервные копии провайдера, фактическую производительность vCPU и расположение дата-центра. Эти условия проверяются до покупки.

## Порядок реализации

1. Проект приложения, локальный PostgreSQL, миграции, вход учителя, список учеников и ограничения доступа.
2. Создание экзамена администратором: силабус, класс 9/10, общее число вопросов и баллов, включенные типы. После публикации каждый выданный код получает персональный вариант через OpenAI API.
3. Персональные коды на выбранный учителем экзамен, выдача вариантов, сохранение и отправка попытки.
4. Кабинет учителя, экспорт, журнал изменений, резервное копирование и тест восстановления.
5. Нагрузочный прогон, затем настройка VPS и домена.
