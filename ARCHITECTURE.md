# Tapsyrma — архитектура на VPS

Статус: рекомендуемая схема, 12 октября 2026. Исходные условия: до 100 учеников одновременно; учитель выбирает ученика и экзамен, затем выдает персональный код на одну попытку; Tapsyrma сохраняет все попытки и показывает баллы, а оценку в EduPage учитель меняет сам. Для генерации заданий используется имеющийся баланс OpenAI API.

## Размещение

Один VPS со скриншота: 3 vCPU, 8 ГБ RAM, 100 ГБ NVMe, 13 250 ₸/мес. На нем размещаются фронт, один API-сервер и PostgreSQL. Supabase и Cloudflare Pages в основной схеме не используются.

```text
Браузер ученика/учителя
          │ HTTPS
          ▼
        Caddy ── статические файлы фронта
          │
          └────── Django/Gunicorn ── PostgreSQL (только внутренняя сеть)
                      │       └── приватные файлы силлабуса
                      └────────── OpenAI API (только подготовка экзамена)
```

Реализация: один проект, три сервиса в Docker Compose (Caddy, Django/Gunicorn, PostgreSQL), постоянные тома для данных. Фронт — страницы Django и небольшой JavaScript для экзамена и автосохранения; отдельная SPA-сборка не требуется. Caddy отдает статические файлы и получает HTTPS-сертификат для домена. Браузер обращается только к Django; соединение с базой и ключ OpenAI в браузер не попадают.

Стек: Python, поддерживаемая ветка Django LTS, PostgreSQL, Gunicorn, Caddy, Docker Compose. Django предоставляет авторизацию, сессии, CSRF-защиту, миграции и административный интерфейс. Для генерации заданий используется официальный Python-клиент OpenAI. Отдельные Redis, Celery, React и Next.js не нужны на первом этапе.

## Вход и права

Учителя и администраторы входят по логину и паролю через Django. Ученик для сдачи не создает аккаунт и не вводит пароль: персональный код служит доступом только к назначенному ему экзамену. Учитель выбирает ученика из списка с постоянным внутренним ID, чтобы ученики с одинаковыми именами не смешивались. Действия учителя и администратора журналируются.

Класс можно хранить у ученика для поиска и отчета, но он не участвует в допуске. Учитель видит только свои экзамены, выданные коды и результаты; ученик по коду получает доступ только к одной назначенной работе. Общий список экзаменов и ключи правильных ответов ученику не выдаются.

## Персональный код на один экзамен

1. Учитель выбирает ученика и один утвержденный экзамен, задает время, до которого можно начать. Система создает отдельное приглашение со случайным кодом из 8 удобочитаемых символов. Код показывается учителю для личной выдачи ученику; в базе хранится HMAC кода с серверным секретом, а не сам код.
2. Ученик открывает страницу сдачи и вводит код. Он видит свое имя, название экзамена и длительность, затем подтверждает старт. Просмотр условий попытку не расходует.
3. При старте сервер закрепляет за приглашением один вариант и одну попытку. Повторный ввод того же кода во время работы возвращает ту же попытку и сохраненные ответы, в том числе после обрыва связи; второй вариант не создается.
4. После сдачи код больше не открывает работу. Если нужна еще одна сдача, учитель явно выдает новое приглашение; первое и все его результаты остаются в истории. Потерянный код активной попытки можно перевыпустить без создания новой попытки.

После окончания времени входа новые старты запрещены, но уже начатую работу можно продолжить до ее срока сдачи. Ввод неверных кодов ограничивается по частоте. Код — единственный секрет ученика: его можно передать другому человеку, и система без входа по аккаунту не докажет, кто именно писал работу. Для суммативов учитель выдает код лично и сверяет ученика в классе; для удаленной сдачи с проверкой личности понадобится дополнительный вход.

## Подготовка экзамена и вариантов

1. Учитель загружает фрагмент силлабуса. Храним оригинал, извлеченный текст и версию; скан проверяется после OCR.
2. Учитель задает спецификацию: требования силлабуса, число заданий по каждому требованию, тип, баллы и уровень сложности.
3. API отправляет в OpenAI API только нужные фрагменты силлабуса и получает структурированные черновики заданий. Данные учеников туда не отправляются. Запуск генерации, версия промпта, число токенов и расход фиксируются. Генерация ограничивается по объему и доступна только учителю.
4. Учитель проверяет формулировку, фактологию и ключ каждого задания. Опубликованный банк неизменяем; исправление создает новую версию.
5. При старте попытки сервер собирает ученику вариант по общей спецификации. Набор идентификаторов заданий имеет уникальную подпись в рамках экзамена. Недостаточный банк обнаруживается до публикации. Варианты могут иметь общие задания; если требуется полное отсутствие пересечений, банк должен быть намного больше.

Равная структура вариантов не доказывает равную фактическую сложность. Уровень сначала утверждает учитель, затем он уточняется по статистике решений для следующей версии банка. ИИ не выставляет окончательную оценку открытым ответам.

## Попытки и результаты

Основные данные: `students`, `exams`, `syllabus_sources`, `blueprints`, `question_versions`, `answer_keys`, `exam_invitations`, `attempts`, `attempt_questions`, `responses`, `results`, `audit_events`.

- `start_attempt` в одной транзакции проверяет приглашение, срок начала и статус кода; сохраняет вариант и версию ключей. Уникальное ограничение базы на `attempt.invitation_id` исключает вторую попытку даже при двух одновременных нажатиях. Повторный запрос возвращает существующую попытку.
- Ответы сохраняются автоматически примерно раз в 10–15 секунд и при переходе между вопросами. Интерфейс показывает статус сохранения; неподтвержденные ответы временно остаются в браузере при обрыве связи.
- `submit_attempt` выполняется одной транзакцией и идемпотентно: повторное нажатие возвращает тот же результат. Время берется с сервера. После отправки ответы не меняются; исправление балла записывается отдельным событием с автором и причиной.
- Попытки со статусами «идет», «сдана», «время истекло» и «отменена» сохраняются вместе с ответами, вариантом, баллами и временем событий. Учитель видит историю ученика и может выгрузить CSV. Перенос оценки в EduPage остается ручным.

## Надежность и эксплуатация

- При 100 учениках и сохранении каждые 15 секунд средняя нагрузка автосохранения составляет около 7 записей в секунду. Это умеренная нагрузка для данной конфигурации при коротких запросах и индексах. Пик одновременного входа и отправки проверяется отдельно; паспортные 3 vCPU/8 ГБ сами по себе не гарантируют результат.
- Ориентир по памяти: до 2 ГБ на PostgreSQL, до 2 ГБ на приложение с несколькими воркерами, остальное — ОС, файловый кэш и запас. Точные параметры задаются после измерения, а не по этой оценке.
- PostgreSQL не открывается в интернет; извне доступны только HTTPS и ограниченный SSH. Секреты хранятся вне репозитория. Обновления ОС и зависимостей выполняются регулярно.
- Ночью создается копия базы через `pg_dump` и копия приватных файлов. Они шифруются и отправляются **за пределы VPS**. После каждого сумматива делается дополнительная копия результатов. Раз в месяц выполняется пробное восстановление.
- Мониторинг проверяет доступность сайта и API, свободное место, память, работу базы и успешность последней резервной копии. До экзамена проводится тест ввода кодов и сохранения на 100 одновременных учеников из школьной сети.
- Один VPS остается единой точкой отказа. Внешняя копия позволяет восстановиться, но не обеспечивает мгновенное переключение при аварии; для важного сумматива нужен запасной порядок сдачи.
- Скриншот тарифа не подтверждает SLA, резервные копии провайдера, фактическую производительность vCPU и расположение дата-центра. Эти условия проверяются до покупки.

## Порядок реализации

1. Проект приложения, локальный PostgreSQL, миграции, вход учителя, список учеников и ограничения доступа.
2. Силлабус, спецификация экзамена, генерация черновиков через OpenAI API и утверждение банка.
3. Персональные коды на выбранный учителем экзамен, выдача вариантов, сохранение и отправка попытки.
4. Кабинет учителя, экспорт, журнал изменений, резервное копирование и тест восстановления.
5. Нагрузочный прогон, затем настройка VPS и домена.
